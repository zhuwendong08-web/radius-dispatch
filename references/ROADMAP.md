# radius-dispatch 后续优化路线（2026-09-05 复盘）

基于全天真实开发与四轮实测（广州体育西路 / 东莞虎门站 / 东莞市中心 / 等时圈联动）
踩过的坑和暴露的短板整理。按「对用户实际找场地的帮助」排序，不按工程趣味排序。

---

## P0 — 直接提升「这次找场地」的成功率

### 1. 到站点步行距离：算 top-3 站点取最优，而非直线最近那一个
**现状**：`enrich` 只找「直线距离最近」的站点做步行算路。
**问题**：直线最近 ≠ 步行最近。实测「田园乐露营」直线 28m 到站点，实际步行 189m——
若直线最近的站点在马路对面/封闭侧，绕路可能让它远不如第二个站点。
**做法**：对每个候选取直线前 3 个站点各算一次步行，取最小。成本：步行 API 调用 ×3
（配额 150k/月，候选通常几十到几百，无压力）。
**收益**：把「到站点距离」从「估算」变「准确」，直接影响硬约束是否误杀。

### 2. 容量从「推断」变「事实」——唯一绕不过去的最后一公里
**现状**：高德不返回面积/人数，容量全靠类型代理 + 人工电话。
**问题**：这是排名里最大的不确定性来源。「能装 200~300 人」是用户核心约束，但现在
只能靠适配度猜，然后把「必须打电话」甩给用户。
**可尝试的数据补全**（按可行性排）：
  a. **高德 AOI 边界**（`/v5/aoi/polyline`，返回面状区域 polygon）——能拿到园区/景区
     真实边界算面积。当前需高级权限，先探一次能不能开；
  b. **候选详情补全**（`/v3/place/detail`）——拿 `biz_ext` 深度信息，部分场地有
     `rating/cost`，可作容量弱信号；
  c. 名称结构化解析——「XX山庄」「XX拓展基地」按业态给面积先验区间，至少能标
     「约可容 X-Y 人」而非笼统 85 分。
**诚实声明**：a/b 是否可用取决于高德权限，若开不了，容量核实只能继续靠人工。

### 3. 联系清单做成正式功能
**现状**：今天生成「联系核实版清单」是一次性内联脚本。
**做法**：`scout --contacts` 直接输出 CSV，含电话/地址/「需人工核实」列
（从 flags 推导核实事项），并在控制台给「Top 5 建议先打」。
**收益**：工具产出的终点从「一份排名」变成「一份能直接执行的动作清单」。

## P1 — 通用化（对齐最初愿景：别人也能用这个 skill 做仓储/网点选址）

### 4. 业务类型配置外置为 JSON
**现状**：`BUSINESS_TYPES` 硬编码在 py 里；扩展新类型（仓储实测、服务网点、充电站…）
要改代码。早期 v1 草稿其实是外置 JSON（config/business_types.json），v2 单文件化时收回了。
**做法**：配置抽到 `config/business_types.json` + 命令行 `--type-file` 支持用户自带配置，
脚本只留加载与默认值。每类配置 = OSM 标签 + amap 关键词 + 四维权重 + 适配度规则 + 默认硬约束。
**收益**：用户不碰代码就能加「自己的业务」——这是「帮助别人」的前提。

### 5. 反馈闭环：核实结果回写，自动调适配度
**现状**：适配度权重是人工拍板的静态规则。
**做法**：用户核实后对候选打标（`可用/装不下/已关`），脚本据此统计「哪些信号词高估/低估」，
给出调参建议或半自动更新 `suitability`。形成「跑 → 筛 → 核实 → 回写 → 越跑越准」的闭环。
**收益**：把一个一次性工具变成越用越懂用户的数据资产。

### 6. 等时圈检索改为网格覆盖，省配额
**现状**：等时圈模式用外接圆（实测 17.3km）做 POI 检索，500 候选里 **193 个（39%）**
在圈外被丢弃——检索请求白花。
**做法**：用若干 5km 小圆覆盖等时圈多边形（多边形填充），逐圆周边搜索合并去重。
**收益**：省 ~40% 周边搜索配额 + 减少无关候选拉低截断质量。

## P2 — 边界能力

### 7. 步行等时圈
**现状**：等时圈只支持驾车。但团建/网点场景「地铁+步行」很常见（用户原话：地铁站口为原点）。
**做法**：复用 `_isochrone_boundary`，把 `_drive_minutes` 换成 `/v3/direction/walking`
（个人 key 已验证可用）。注意步行可达范围小（20 分钟约 1.5~2km），方向采样 16 即可，
请求量比驾车更少。
**收益**：补齐「短途步行可达」这一半语义，和驾车等时圈互补。

### 8. OSM 免费层的强化（无 key 用户的体验）
**现状**：OSM 无步行/驾车距离（直线）、中国场地 POI 稀疏。
**可做**：OSM 有 building/landuse 多边形可算面积（v1 原型已实现），把「面积维」接回
OSM 打分（目前高德模式面积恒 0，OSM 模式下其实有）。同理容量代理在 OSM 下用
`capacity_proxy` 已实现。OSM 端主要差在步行距离——可考虑 OSRM 公共实例（免费，需试探连通）。

### 9. warehouse / service-outlet 真实数据实测
**现状**：这两种类型已内置配置但从未用真实高德数据跑过（team-building 跑烂了）。
**做法**：各挑一个原点实测，重点验「适配度词表」对仓库/网点生态是否偏科
（大概率会像市中心暴露手作馆一样暴露新问题）。**这是通用化之前必做的一步。**

## 明确不建议做的（诚实声明）

1. **爬大众点评/美团补容量与评分**：违反平台条款、易封 IP、数据权属不清。这个工具要开源
   给别人用，不能背上合规风险。替代：引导用户在看中的场地时自行参考点评。
2. **追求 POI 真实建筑面积**：高德 Web 服务就是不返回，这是数据源硬边界，不是实现问题。
   AOI/详情能拿多少是多少，拿不到就维持「人工核实」。

---

## 优先级建议

- 先做 **P0-3（contacts 正式化）** 与 **P0-1（top-3 站点步行）**：改动小、直接改善本次选场地体验；
- 再做 **P0-2 容量补全的权限探测**（AOI/detail 能不能开，决定容量这条路能走多远）；
- 通用化（P1）里先做 **P1-9（另两类真实实测）**，再外置配置——避免把没验证过的配置外置出去。
